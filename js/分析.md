## 2. 签名算法（已复刻）

`xlplayer.js` 剥掉 `_0x` 混淆后是标准的 md5 + AES-ECB：

```js
const t   = Date.now();
const key = CryptoJS.enc.Utf8.parse(md5(pid + "-" + t).substring(0, 16));
const enc = CryptoJS.AES.encrypt(pid + "-" + t, key, {
    mode: CryptoJS.mode.ECB, padding: CryptoJS.pad.Pkcs7
});
sg = base64ToHex(enc.toString());      // ciphertext -> hex -> 大写
```

```python
def sign(pid, t):
    key = hashlib.md5(f"{pid}-{t}".encode()).hexdigest()[:16].encode()
    p = pad.PKCS7(128).padder()
    d = p.update(f"{pid}-{t}".encode()) + p.finalize()
    e = Cipher(algorithms.AES(key), modes.ECB()).encryptor()
    return (e.update(d) + e.finalize()).hex().upper()
```

> **坑**：`t` 必须是整数毫秒。传浮点（`time.time()*1000`）→ 服务端 **400**，因为 sg 里的 t 与表单里的对不上。

## 3. 完整链路（全部实测）

```
① GET  /lines?t=&sg=&pid=            → 线路表
② 选线（见第 4 节，必须选对！）
③ GET  <线路url>，www.bde4.cc→站点域名
   → 载荷 = 真 PNG 前 3354 字节 + gzip 数据（伪装成图片绕识别）
④ 丢前 3354 字节 → gunzip → 明文 m3u8（938 段）
⑤ 分片地址：https://vod.xl01.me/[hls/]<name>.ts
   命中 ac5634-us / 4102-us 的线路要加 /hls/，其余不加
⑥ 分片实测：HTTP 200，1.6~10 MB，Content-Type video/mp4，TS 流（0x47 同步字节）、938 段、时长 9382 秒
```

### 线路表返回样例

```json
{"code":0,"data":{
  "url3":"https://v.xl01.eu.cc/obj/<HASH>,https://v16m-default.akamaized.net/...",
  "m3u8":"https://www.bde4.cc/<HASH>.m3u8#maliva",
  "m3u8_2":"...m3u8#ac5634-us,...m3u8#tos_hls3,...m3u8#iplay,...m3u8#yvqzo4",
  "tos":"1","ptoken":"888"}}
```

### 备用线路

`POST /god/{pid}?type=1` → `{"url":"http://lf16-secsdk.bitssec.com/obj/tos-maliva-o-0000-us/...?x-expires=...&x-signature=..."}`

- 带 `?type=1` **完全跳过验证码**（`switch2()` 只对不含 `type` 的线路弹验证码/判 24 小时/判会员）
- 时效约 **27 秒**，CDN 主机名每次随机轮换
- 该直链直接 GET 返回 **403**（防盗链 + 时效太短），实用价值低

## 4. ★ 关键：必须选对线路

`m3u8` 与 `m3u8_2` 里每条线路的可用性**完全不同**（实测）：

| 来源 | tag | 段数 | 分片实测 |
|---|---|---|---|
| m3u8 | `maliva` | 938 | ❌ 返回 1.66MB PNG 占位图 |
| m3u8_2 | `ac5634-us` | 938 | ✅ octet-stream，TS 流（走 `/hls/` 前缀） |
| m3u8_2 | `tos_hls3` | 938 | ✅ octet-stream，TS 流 |
| **m3u8_2** | **`iplay`** | 938 | ✅ **video/mp4，TS 流 —— 播放器实际在用的就是这条** |
| m3u8_2 | `yvqzo4` | 938 | ❌ 返回 image/bmp 占位图 |

**这正是最坑的地方**：随机取一条线路（比如 `data["m3u8"]`）会得到占位图，误判成"站点坏了"。实际是线路级差异 —— 站点把失效线路留在列表里当"备胎占位"。

判定方法：取分片后看 `Content-Type` 与首字节。
- 真数据：`video/mp4` 或 `application/octet-stream`，首字节 `47 40 11 10`（TS 同步字节 0x47）
- 占位：`image/png` / `image/bmp`，首字节 `89 50 4e 47` / `42 4d`

## 6. 写成 TVBox js 源的方案

### 已解决的环节

| 环节 | 做法 |
|---|---|
| 分类/列表/详情 | 静态 HTML，标准 `一级/二级` 选择器 |
| 线路表 + 签名 | `request()` GET `/lines`，md5+AES-ECB 生成 `sg` |
| m3u8 解密 | 需要**自备 gunzip**（源环境无 pako） |
| 选线 | 优先 `iplay`，回退 `tos_hls3` / `ac5634-us`，跳过 `maliva` / `yvqzo4` |
| 分片 | `https://vod.xl01.me/[hls/]<name>.ts`，**不需要额外 header 或 cookie 即可直取** |

### 仍需处理的难点

1. **gunzip**：内联一个纯 JS inflate（fflate 的 `ungzip` 约 3KB），源体积主要来自这里
2. **二进制**：要确认 QuickJS 的 `request()` 能否返回 `arraybuffer`；只能给文本的话需要 base64 通道
3. **伪装头剥离 + 分行重写**：`bytes[3354:]` → gunzip → 把每行 `.ts` 前缀成绝对地址
4. **回传给播放器**：playlist 走本地代理（`getProxyUrl()` + `proxy_rule`）或 `data:application/vnd.apple.mpegurl;base64,`。好消息是**分片可以直接用绝对地址**（实测无鉴权），不必为分片再写一层代理 —— 这大幅简化了实现

### ⚠️ 代理地址：已在宿主源码层面验证（并修掉一个真 bug）

原来我拼的是 `getProxy(true) + '?do=csp&siteKey=...'`。**读宿主源码后发现这是错的**：

```java
// FongMi/TV  quickjs/.../method/Global.java:106
public String getProxy(Boolean local) {
    return Proxy.getUrl(local) + "?do=js";     // ← 已经自带 ?do=js
}

// FongMi/TV  app/.../api/loader/BaseLoader.java:79
public Object[] proxy(Map<String, String> params) throws Exception {
    if (params.containsKey("siteKey")) return getSpider(params.get("siteKey")).proxy(params);  // ← 有 siteKey 就直接路由到本源
    if ("js".equals(params.get("do"))) return jsLoader.proxy(params);
    if ("py".equals(params.get("do"))) return pyLoader.proxy(params);
    return jarLoader.proxy(params);
}
```

两个结论：

1. `getProxy()` 返回值**已含 `?do=js`**，再拼 `do=csp` 会产生 `?do=js&do=csp` 这种重复参数 —— 已修正为只用 `&` 追加 `siteKey` 和自定义键
2. **带 `siteKey` 时第一分支直接命中本源**，`do` 参数根本用不到 —— 所以正确的形式就是
   `http://127.0.0.1:<port>/proxy?do=js&siteKey=<skey>&k=<key>`

修正后实测地址（测试台输出）：
```
http://127.0.0.1:9978/proxy?do=js&siteKey=xltest&k=p204736_1789362768597
```
测试台还按 `BaseLoader.proxy()` 的逻辑模拟了一遍路由判定 → 命中 `by-siteKey`。

签名相关的宿主语义也已核对源码确认：`md5X`→`Crypto.md5`（**小写** hex）、`aesX`→`Crypto.aes`（`outBase64=true` 时返回 `Base64.NO_WRAP`），与源里的实现完全对应。

## 7.5 分片验证（补测）

`vod.xl01.me` 的分片**完全无鉴权**，带不带 Referer 都一样：

| 分片 | HTTP | 大小 | Content-Type | 首字节 |
|---|---|---|---|---|
| #0 | 200 | 1,662,860 B | `video/mp4;charset=UTF-8` | `0x47` ✓ TS |
| #1 | 200 | 6,872,716 B | `video/mp4;charset=UTF-8` | `0x47` ✓ TS |
| #2 | 200 | 5,756,936 B | `video/mp4;charset=UTF-8` | `0x47` ✓ TS |

两种返回都遇到过，播放器都能处理：

- **200 直接返回 TS 数据**
- **302 跳到真 CDN**（如 `https://f2.iplay.126.net/obj/...`），跟跳即可

> 注意：本机的 mingw 版 curl 连该 CDN 会报 `TLS error 35`（环境问题，非链路问题），
> 所以分片验证用 Python 的 TLS 栈做（`复验分片.py`）。

### ★★ 分片 CDN 校验 User-Agent —— 会真机翻车的坑

用 ffmpeg 取分片时发现：

| 请求方 | 结果 |
|---|---|
| ffmpeg 默认 UA（`Lavf/8.1.2`） | **HTTP 403 Forbidden** |
| 浏览器 UA | HTTP 200，正常 |

**CDN 对 User-Agent 做了校验。** 播放器如果用自己的默认 UA 去拉分片就会 403。

→ 已在源里修正：`play()` 的返回值带上 `header: { 'User-Agent': <Chrome UA> }`，
让播放器取分片时携带该 UA。

## 7.6 ffmpeg 真实解码验证（最终证明）

把前 3 段（共 30 秒）连同它们的 `#EXTINF` 落到本地，生成纯本地 m3u8，再交给 ffmpeg：

```
ffprobe segs/local.m3u8
  → video: h264, 1920x1080
  → audio: aac, 48000 Hz, 2 ch
  → format: hls, duration = 30.083333

ffmpeg -i segs/local.m3u8 -f null -     → ✓ 完整解码，零错误
```

`30.083333 = 12.083333 + 12.000000 + 6.000000` —— **与我们解出的 `#EXTINF` 之和完全吻合**。

结论：**解出来的播放列表描述的是真实、可解码的 1080p H.264 + AAC 视频流**，
不是占位数据、不是坏流。整条链路（签名 → 线路 → 解密 → 分片）已被证明产出可播放的媒体。
